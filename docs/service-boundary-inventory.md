# Service Boundary Inventory

Inventory of the current `src/services/*.ts` modules to map coupling before Moleculer refactoring.

## Classification legend

- **same-domain** — internal helpers or repository-only orchestration inside one bounded area.
- **synchronous action** — request/response operation that should stay sync for now.
- **asynchronous event candidate** — side effect or notification-like flow that can later become an emitted event or event handler.

## Future action / event examples to keep in mind

- **Future Moleculer actions**: `users.bootstrap`, `wallets.topUp`, `matching.searchRoutes`, `notifications.markRead`, `journeys.cancel`, `journeys.complete`, `journeys.getSummary`.
- **Notification emits**: all `emitNotification(...)` call sites are **asynchronous event candidates**.
- **Transaction-heavy flows that stay synchronous for now**: `groupOffer.accept`, `groupRequest.cancel`, `routeRequest.accept`, `routeRequest.decline`, `routeRequest.cancel`, `journeys.cancel`, `journeys.complete`.

## Coupling hotspots

1. **`userService.ts` fan-out** — central orchestrator for review, report, notification, and role checks. This is the main cross-service coupling point.
2. **Notification emission pattern** — `routeRequestService.ts`, `groupOfferService.ts`, and `groupRequestService.ts` all emit notifications inline after state changes. These are strong candidates for later event/outbox extraction.
3. **Transaction-heavy acceptance/cancellation flows** — `groupOffer.accept`, `groupRequest.cancel`, `routeRequest.accept`, `routeRequest.decline`, `routeRequest.cancel`, and `journeyService` trip mutation methods combine state changes with fan-out side effects or summary-building. Keep them synchronous until the transactional contract is explicitly redesigned.
4. **`driverRouteService.publishRoute` + wallet coupling** — route publication depends on wallet fee computation, so route publishing and wallet policy should stay aligned during refactor.
5. **`journeyService.getJourneySummary`** — pulls route/plan plus accepted counterpart state and review eligibility in one read path; this is the clearest future contract seam for a `journeys.getSummary` action.
6. **`matchingService.searchRoutes`** — already a clean action-shaped entry point, but it depends on the matching module rather than repositories directly, so it is a good first Moleculer action candidate.
